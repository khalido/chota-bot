# Chota Review

## Summary

Chota is in a good shape for a first public commit because it is already anchored around one real shipped loop: a weekday morning print that the family can actually use. The strongest parts of the project are the small typed tool wrappers, the `chota.config.ts` family-config pattern, the plain-text-plus-image print pipeline, and the per-file job model. Keep protecting those choices.

The main risks are not architectural complexity in the app. They are repo hygiene, docs drift, and accidentally publishing private local artifacts. Before going public, scrub `py/`, ignored/generated outputs, local agent settings, and stale docs that describe old plans as current behavior.

For future plans, prioritize features that make the morning routine more reliable and more useful before adding chat/voice novelty. The best next work is operations hardening, better family-specific signals, and a small on-demand print menu. Agent and voice should land only once they can improve a concrete workflow, not just exist as a chat box.

## What Is Working

- The project has a clear center of gravity: the morning print. That keeps decisions grounded and prevents a vague smart-home dashboard from sprawling.
- Tools are plain TypeScript functions, not framework objects. That keeps them testable, reusable from routes/jobs/agents later, and easy for a forker to understand.
- `chota.config.ts` is the right abstraction for a family-run kiosk. It is typed, easy to edit, and avoids a premature settings UI.
- The print pipeline has the right fallback hierarchy: structured data, plain text, styled HTML screenshot, canvas fallback, USB transport. That is pragmatic for hardware.
- The job system is simple enough to trust. One file per job plus `defineJob()` is the right scale for a local kiosk.
- The docs capture decision history well. They are useful for the original maintainer and for future agents working in the repo.

## Before Public Release

- Treat repo hygiene as the release blocker. Scrub or remove `py/libs/` private examples, local `.claude` settings, ignored config, generated build outputs, and private docs from anything that could be committed.
- Make docs distinguish “built” from “planned” more aggressively. Public readers forgive planned features; they get frustrated by docs that say something exists when it does not.
- Align setup ports and OAuth docs. The code uses port `8000`, while some docs still say `5173`.
- Replace stale config references like `data/config/family.json` with `chota.config.ts`.
- Remove live-looking stubs unless they provide immediate value. The `dreaming` and `heartbeat` jobs are explainable internally, but public readers will see them as unfinished scaffolding.

## Architecture Advice

Keep the architecture boring. This project wins by being understandable: SvelteKit routes, typed tools, typed family config, local SQLite, cron jobs, one USB printer.

The biggest architecture mistake would be adding a plugin system, multi-tenant config, a generic workflow runner, or an agent framework before a second real user forces it. Forkers can edit Svelte files and config directly. That is a feature, not a limitation.

The second biggest mistake would be letting the agent become the center of the system. The deterministic morning data should remain deterministic. The agent should add judgment, summarization, and memory only where it clearly improves output.

The best long-term boundary is:

- Tools fetch and normalize data.
- Composers decide what matters for a specific surface.
- Renderers make it printable or glanceable.
- Jobs decide when work happens.
- Agents propose or summarize, but do not own core household truth.

## Operations Advice

The next high-leverage work is reliability, not more integrations.

- Add a durable `job_runs` table once you care about “did it print today?” after restarts.
- Add a 06:50 watchdog only after `job_runs` exists. It should alert on no successful 06:45 print.
- Implement LogTape or keep the current logger, but make the docs match reality. Do not leave both as “current.”
- Add a simple `/admin/health` or improve `/admin/jobs` to show printer visibility, last successful print, Google auth status, Sentral cookie freshness, and cache ages.
- Keep manual deploy for now. It is appropriate for a family kiosk with a hardware side effect.

## Security And Privacy

The current local-trusted model is fine for a wall kiosk. It is not fine for public internet exposure.

Document that clearly for forkers: `/admin`, `/api/print/*`, and `/api/sentral/*` are trusted-LAN surfaces until route gating lands. Better Auth is wired, but not used as an authorization boundary yet.

Keep the rule that real names live only in `chota.config.ts`. Also extend that rule to old reference code, docs, screenshots, generated build outputs, and agent settings.

## Future Plans

### Phase 2

The print menu is the best Phase 2 feature. It fits the physical object, it is useful without chat, and it exercises the print pipeline in small increments.

Recommended order:

1. Add a small set of reliable print formats: today, kid brief, shopping list, week calendar, puzzle answer.
2. Add evening or “tomorrow prep” print once the morning print is stable.
3. Add family-specific signals like bins, school holidays, canteen/lunch, gear packing, and rain-at-pickup.
4. Add the agent only for a specific slot: a closing line, tomorrow reminder, or “what matters today” summary.

Avoid starting Phase 2 with a generic chat surface. It will produce demos before it produces household value.

### Phase 3 Voice

Voice is worth doing if it targets short commands:

- “Print today again.”
- “Add milk to shopping.”
- “What time is Kid1’s first class?”
- “What should Kid2 pack today?”
- “Tell me the bus times.”

Start push-to-talk. Do not start wake-word or ambient listening. Kitchens are noisy, and always-listening family devices raise trust questions quickly.

### Telegram

Telegram is a good remote-control surface, not necessarily the main conversational product. Long polling and a chat-ID whitelist are the right decisions.

Use it first for alerts and small commands:

- Morning print failed.
- Sentral cookie expired.
- “Print shopping list.”
- “Add X to TickTick.”
- “What is on tomorrow?”

Streaming chat can wait. Alerts and commands will pay off sooner.

### Agent Memory

File-based JSONL memory is a good fit, but only if the agent writes very little. Prefer explicit memory events over broad transcript capture.

Good memory:

- “Kid1 has swimming on Tuesdays and needs goggles.”
- “Parent2 prefers no printer chatter after 8pm.”
- “Family likes short jokes, not riddles, on school mornings.”

Bad memory:

- Full chat transcripts.
- Raw tool results.
- Every calendar event.
- Anything that duplicates source-of-truth systems like TickTick or Google Calendar.

## Useful Feature Ideas

### Highest Leverage

- **Tomorrow prep print:** runs around dinner or bedtime with tomorrow’s first event, school notes, weather, gear, lunch/canteen reminders, and bins.
- **Sentral cookie freshness:** show last refresh success and obvious “cookie expired” status in `/admin`.
- **Rain-at-school-pickup signal:** more useful than generic weather; print “umbrella for pickup” when rain overlaps departure/pickup windows.
- **Packing checklist:** calendar event title plus `activities` config maps to gear lines.
- **School holiday / pupil-free suppression:** avoid printing school bus and class sections on non-school days.

### Good Phase 2 Additions

- **Shopping list print:** one button, useful immediately, no AI needed.
- **Puzzle answer print:** lets the receipt include a puzzle without spoiling it.
- **Weekly ops receipt:** tiny Sunday status print: prints succeeded, failures, stale auth, cache status.
- **Calendar picker admin helper:** make it easier to copy the right Google Calendar ID into config.
- **Printer smoke test in admin:** visible device IDs plus a print button.

### Agent-Friendly Features

- **Closing-line generator:** bounded prompt, deterministic body stays untouched.
- **Tomorrow summary:** agent compresses calendar plus memory into one useful note.
- **TickTick add command:** voice/Telegram command to add to configured family lists.
- **News/fact summarizer:** only after caching and filtering are in place.

### Defer

- Full conversational kiosk screen.
- Agent-generated mini apps.
- Banking announcements.
- Calendar mutation.
- Plugin systems or config UI.
- Web search as a general-purpose tool.

## Ideas Worth Salvaging From `py/libs/`

The Python folder should not be treated as production architecture, but it does contain useful product ideas and edge-case knowledge from v1. Port ideas, not code structure.

### Port Soon

- **Imminent event detection:** `dashboard_image.py` promotes events happening within 2 hours. This is more useful than a flat calendar list. Add a deterministic helper that marks events as `now`, `soon`, `today`, `tomorrow`, or `later`, then use it on the dashboard and print.
- **Bus delay / occupancy / alerts language:** `transport_nsw.py` cared about delay, early/late running, occupancy, transfers, and alerts. The TS bus tool already has cancellations and realtime status; add delay/early copy if TfNSW exposes the fields in the current endpoint.
- **Weather alerts:** `google_weather.py` had a `publicAlerts:lookup` path. Google alerts may be patchy in Australia, but the product idea is good: severe-weather notices should override normal dashboard styling and print copy.
- **Weather “what to bring” framing:** v1’s weather prompt focused on umbrella, sunscreen, jacket, and outdoor timing. Keep that product lens, but implement most of it deterministically with thresholds instead of using an LLM every time.
- **Energy status summary:** `enphase.py` has a clean shape: production now, consumption now, import/export now, production today, status. That would make a good dashboard card and occasional kid-friendly science fact.
- **Energy diagnostics:** per-inverter status is not daily-kiosk content, but it is good `/admin` health content if Enphase lands.

### Good Later

- **Savings targets:** `bank_metadata.py` stores account metadata and targets. If banking ever lands, “goal progress” is more family-friendly than raw balances. A “climb fund” or kid savings goal could be a nice occasional print section.
- **Account metadata cache:** account IDs are ugly and stable; names and target notes are human. If banking is built, keep a small local metadata table for aliases, display names, and goals, while treating live API balances as source of truth.
- **Generated image safety pattern:** `gen_image.py` does a pre-flight safety check and applies a warm family-friendly style suffix. If image generation returns, keep the safety-gate idea, but prefer provider safety plus strict use cases over open-ended kid prompts.
- **Dashboard cleanup policy:** `dashboard_image.py` has sparse-history cleanup for generated PNGs. The current app should not generate dashboards that way, but the cleanup idea is useful for any future screenshots, print previews, or local media cache.
- **Markdown formatting helpers:** `llm_utils.py` has a simple pattern of formatting structured data before summarization. In TS, this should be tiny local helpers near each agent job, not a global “LLM utils” abstraction.

### Do Not Port Directly

- Do not revive the Gemini-generated whole-dashboard image as the main UI. Svelte components are more reliable, inspectable, and accessible.
- Do not port Python env names or token-file OAuth flows. The SvelteKit app’s Better Auth setup is the current direction.
- Do not port raw banking display. If money appears, it should be opt-in, goal-based, and conservative about what shows on a family-room screen.
- Do not port direct Anthropic calls. Future AI calls should go through AI Gateway except voice transcription.
- Do not preserve real-name examples from `py/libs/`. Scrub them before publishing or delete the folder from the initial public commit.

## Docs Advice

Keep `README.md` short and accurate. It should be the forker path.

Keep `CLAUDE.md` operational. It should tell agents where to look and what conventions must not be broken.

Keep `docs/plan.md` as decision history, but trim present-tense claims about unbuilt systems. A public reader should never have to guess whether something is shipped.

Move brainstorm-heavy material into clearly marked “ideas” docs. The inspiration, strategy, logging, Telegram, and agent docs are useful, but they should not read like required setup for Phase 1.

## Product Direction

The strongest public story is not “AI family dashboard.” It is:

> A local-first family kiosk that prints a useful morning receipt.

That is concrete, charming, and technically understandable. AI is a supporting ingredient later, not the hook. The printer gives the project its personality and makes it different from generic dashboards.

For forkability, optimize for “one weekend to get a basic version running”:

- Weather only.
- Optional bus.
- Optional calendar.
- Optional printer.
- Clear degraded states when keys are missing.

If the repo can boot with just `chota.config.ts`, `.env`, and one API key, more people will try it.

## Guiding Principles

- Ship routines before conversations.
- Prefer deterministic output with small agent flourishes.
- Keep family truth in existing systems: config, calendar, TickTick, Sentral.
- Use AI for summarization and judgment, not authority.
- Make local-first the default and public-internet exposure an explicit advanced mode.
- Keep every abstraction explainable to a tired parent at 7am.
