## Big picture (10 Nov)

**The print side is the product today, and it works.** The Pi recorded 3,784 job runs in 30 days with 7 not ok. The chat agent is built wide and barely used: the Pi's database holds 4 agent runs in 2 sessions since the session tables went live on 7 Nov, all on WhatsApp, averaging 1.3 steps and 8,200 input tokens each, half a cent a run, none of it cached. The design notes below (compaction, project agents, dreaming, session affinity, a second runtime) are far ahead of that evidence.

**The biggest risks are not about agents:** one SD card holding the only database (one copy was pulled to the Mac on 10 Nov, `~/chota-backups/`; nothing does it nightly), Kit 3 not yet on the Pi, and a deploy script whose build swap, schema push and put-back have only run in a scratch clone.

**Against Anthropic's [Building Effective Agents](https://www.anthropic.com/research/building-effective-agents)** (Dec 2024; the page itself says its tooling notes have dated). Its three principles are simplicity, transparency, and a carefully built tool interface, and its standing advice is to add complexity only when it measurably helps.

**What that means for the plans:**

- Compaction, dreaming and reminders are workflows: fixed steps in code with one model call each, not tool loops. A reminder that only sends text needs no model.
- Project agents are the article's orchestrator-workers, which it reserves for work whose subtasks can't be known ahead. Nothing a family has asked chota so far fits that. Park it until a real request does.
- Session affinity, a second runtime (libfx, a harness) and prompt caching solve costs chota doesn't have at half a cent a run. Park them.
- The one large missing ability is plain: chota can't message first. That is the reminder and user-jobs work, and it is a workflow.

A GitHub release publishes it, with KO approving by 2FA; the steps are in its `docs/publishing.md`, if chota ever publishes a package. `bunfig.toml`'s 2-day release wait is off (8 Nov), so a fresh publish installs at once. Install it as `"@khalido/home": "latest"`, not a caret range (KO, 8 Nov: both libraries are being built together, so chota takes every release, 0.x minors included; `bun.lock` still fixes what a deploy installs). Pin it once the API settles. It already exports `energyNow`, `bestWindow`, `health` and `onChange`. Before a solar screen: the Enphase gateway refused connections on 28 Oct, and Hue isn't paired.
- **kotools vs our own code:** chota's own libs for anything daily or touching family data; `@khalido/home` for house devices (the Brother laser once it has a print action); `ko` commands wrapped as typed tools only for rare, hard jobs (`ko fetch` as a last resort, `ko gsheets/gdocs/drive`), never a shell.
- **Sentral:** two GETs change state (`markNewsletterAsRead`, `markHomeworkCompleted`); never call them.
- **WhatsApp:** never restart on a long `connecting`; 401 = re-pair. `scripts/whatsapp-spike.mjs` for one-off sends (stop the app first).
- **Shell:** no `pgrep -fl` (prints env secrets); macOS has no `timeout`, use `perl -e 'alarm shift; exec @ARGV' 20 cmd`. Tests with real model calls need an assertion (`expect.assertions`) or vitest marks them failed. Booting the build on the Mac: `TELEGRAM_BOT_TOKEN= WHATSAPP_ENABLED= PORT=8123 bun build/index.js` (the X230 owns the bot).
- **Private, gitignored:** `chota.config.ts`, `.env`, `data/whatsapp-auth/`, `data/files/`. `docs/page-watch.md` is a kotools draft, uncommitted on purpose.
